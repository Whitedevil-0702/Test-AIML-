# Contributing and Team Workflow

## Learner workflow

1. Read the module README and prerequisites.
2. Study the primary resource and record brief notes in your own words.
3. Complete the exercise before viewing a solution, if one exists.
4. Run or manually verify your work.
5. Write a short explanation: what you did, why it works, and one limitation.
6. Create a branch using `learner/your-handle/module-task`.
7. Commit the work and open a pull request (or submit it to the designated mentor if forks are used).
8. Request review from a teammate or mentor.
9. Address feedback and resubmit.
10. Update your progress record only after the evidence has been reviewed.

## Pull-request checklist

- [ ] I can explain the solution without reading the code line by line.
- [ ] I included the required files and a useful README or notebook explanation.
- [ ] I checked the output and relevant edge cases.
- [ ] I did not commit API keys, passwords, private datasets, or personal information.
- [ ] I recorded the source resources used.
- [ ] I identified limitations or assumptions.
- [ ] My progress record reflects the actual status.

## Reviewer checklist

- [ ] Does the submission meet the stated objective?
- [ ] Is the reasoning understandable?
- [ ] Is the output correct for the provided examples and edge cases?
- [ ] Is the evaluation method appropriate?
- [ ] Are data leakage, privacy, and bias concerns addressed where relevant?
- [ ] Are review comments actionable?
- [ ] Is the completion status supported by evidence?

## Status definitions

- `Not Started`: no work submitted.
- `In Progress`: learning or implementation underway.
- `Submitted`: review requested.
- `Changes Requested`: reviewer identified changes needed.
- `Approved`: rubric requirements satisfied.
- `Blocked`: learner needs prerequisite help or resource clarification.

## Branching note

Use a fork-and-PR workflow if learners do not have write access to the main repository. Never commit directly to the protected/default branch for assessed work.
